Quill — notes & a shared board for the household

A Google Keep–style notes module for Howard: colourful tiles in a masonry board that you can pin, reorder by dragging, tick off, search and format. Each partner gets private notes, and there is a shared board for things like shopping lists, passwords-for-the-sitter and gift ideas, kept in live sync across every device by the existing SSE channel.

1Overview & goals

Howard already tracks pet medicine, mantis care, calendars, bills and a caregiver guide, but there is nowhere for the small, messy, everyday stuff: a shopping list, a half-remembered recipe, a note for whoever is feeding the cat. Quill fills that gap as the eighth module, built entirely on the patterns the other seven already use.

Goals

  • Keep-like tile board: masonry layout, pinned section, coloured notes.
  • Drag to rearrange with mouse, touch and keyboard.
  • Text and checklist notes with light formatting.
  • Shared board for both partners plus private notes per person.
  • Live sync, archive, trash and search.
  • Matches both themes, works on phone, tablet and desktop.
  • Zero new runtime dependencies.

Non-goals (for now)

  • Images, drawings, audio and file attachments.
  • Offline editing with later merge (Howard is a LAN app).
  • Real authentication. Howard stays “low-security by design”.
  • Full WYSIWYG rich text (see section 5).
  • Push notifications / time-based reminders.
  • Public share links.
Note

Security stays in line with the rest of the app: the server trusts the profile query/header, and privacy is enforced by server-side projection (like Floodgate) so private notes never leave the server for the wrong profile. It prevents casual snooping on a shared tablet, not a determined attacker on the LAN.

2How it fits Howard

Quill follows the existing module recipe exactly, so there are no new architectural ideas to learn or maintain.

Frontend today

  • React 19 + Vite 8 + Tailwind v4 with semantic tokens (--surface-card, --border-strong …) and the Warm Beige / Softened Dark themes in src/index.css.
  • App.jsx lazy-loads each module and passes activeProfile, darkMode, showToast and onGlobalSync.
  • APP_REGISTRY in moduleStatuses.js drives the sidebar, Ctrl+K switcher and status badges.
  • Shared primitives in HowardUI.jsx: SectionCard, ModuleHeader, SegmentedTabs, ModalShell, ConfirmModal, EmptyStateCard.
  • lucide-react, react, react-dom are the only runtime deps.

Backend today

  • Plain node:http; server/http.js chains the domain handlers (howard, cadence, floodgate, bloom).
  • Node 22 built-in node:sqlite in one data/howard.db; rows are id + JSON data + updated_at.
  • cache.js keeps per-domain revisions, bumpRevision() and an SSE broadcast. Clients hold a sync token and receive partial payloads.
  • Versioned migrations (user_version currently 5) and daily VACUUM INTO snapshots.
  • Profiles (partner1, partner2, caregiver) carry an allowedApps list.

4Spaces & privacy

Every note has visibility ('shared' or 'private') and an ownerProfileId. The four tabs are views over that data:

  • Shared Board – notes both partners can read and edit.
  • My Notes – private to the active partner. The other partner never receives them.
  • Archive and Trash – the same split, filtered by status.

Optionally, a shared note can be flagged caregiverVisible. The Caregiver profile then gets a read-only House Notes view (sitter instructions, bin day reminders) and may tick checklist items. This is a Phase 4 item and an open question.

Permission matrix

ActionOwner partnerOther partnerCaregiver
Read shared noteYesYesOnly if caregiverVisible
Create / edit / archive / trash shared noteYesYesNo
Tick a checklist item on a shared noteYesYesOnly if caregiverVisible (optional)
Read / edit a private noteYesNo (404)No (404)

Important

The server answers 404, not 403, for someone else’s private note so it never confirms the note exists. Projection happens in the cache layer, the same way projectHowardStateForProfile already hides Partner 2’s private Almanac events.

6Tiles & drag-and-drop

Masonry layout that keeps reading order

CSS columns fills top-to-bottom, so the “first” note ends up in the first column’s top and the second note below it, which feels wrong for a board you rearrange. Instead Quill uses a CSS grid with small implicit rows:

/* grid container */
display: grid;
grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
grid-auto-rows: 8px;
gap: 0 12px;

/* each tile, after a ResizeObserver measures its content height */
grid-row-end: span N;   /* N = ceil((height + rowGap) / (8 + rowGap)) */
  • Columns: 2 on mobile, 3 on tablet, 4–5 on desktop (minimum tile width about 220 px).
  • Pinned and Others are separate grids with a small section label.
  • Tile previews clamp at about 12 lines with a fade-out. Checklists show the first 8 items plus “+N more”.
  • Height measurements are batched in requestAnimationFrame to avoid resize jank.
  • Hover (or long-press on touch) reveals quick actions: pin, colour, archive and a “more” menu.

Moving tiles

A custom useNoteDrag hook using Pointer Events. It works identically for mouse, pen and touch. HTML5 drag-and-drop is rejected because it has no touch support.

  1. Grab. Mouse: press and move 6 px. Touch: long-press 250 ms, so normal scrolling is not hijacked. A small haptic vibration is requested where supported.
  2. Lift. The tile becomes a floating ghost (slight tilt, shadow) following the pointer, and a dashed placeholder holds its slot.
  3. Hover target. The nearest tile centre under the pointer decides the insertion index; the grid reflows live.
  4. Auto-scroll. Within about 80 px of the viewport top or bottom the page scrolls.
  5. Drop. Dropping inside the Pinned grid pins the note, dropping in Others unpins it. One reorder request is sent with the new position.
  6. Cancel. Esc or dropping outside returns the tile to its slot.

Keyboard & screen-reader alternative

  • Tiles are focusable. Alt+←/→ move the note one place; Alt+Home/End move to start or end.
  • The “more” menu has Move to start and Move to end.
  • An aria-live="polite" region announces “Shopping list moved to position 2 of 7”.

Ordering with fractional positions

Each note has a position REAL. Moving a note writes one row: its new position is the midpoint of its new neighbours (or ±1000 at the ends). When a gap shrinks below 1e-6 the server renormalises that section to 1000-step spacing. Pinned and unpinned notes are ordered independently, and the shared board and each person’s private board each have their own ordering.

Fallback

If a hand-rolled drag system proves fiddly on real phones, @dnd-kit/sortable is the fallback. It would be Quill’s first runtime dependency beyond React and lucide, so it is flagged as an open question.

7Data model

One new table, created in server/db.js with CREATE TABLE IF NOT EXISTS like the others. Migration v6 backfills 'quill' into each profile’s allowedApps and sets user_version = 6. Indexed columns hold what the board queries on; everything else stays in the JSON blob, as elsewhere in Howard.

Warning — table name pitfall

migrateV3ConsolidateLegacyDatabases runs DROP TABLE IF EXISTS notes; on any database below schema version 3 (including fresh installs). A table called notes would be silently dropped on first boot. Quill’s table is therefore named quill_notes, and a test should assert that the name stays safe.

CREATE TABLE IF NOT EXISTS quill_notes (
  id               TEXT PRIMARY KEY,
  owner_profile_id TEXT NOT NULL,
  visibility       TEXT NOT NULL CHECK (visibility IN ('shared','private')),
  status           TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','archived','trashed')),
  pinned           INTEGER NOT NULL DEFAULT 0,
  position         REAL NOT NULL,
  revision         INTEGER NOT NULL DEFAULT 1,
  data             TEXT NOT NULL CHECK (json_valid(data)),
  updated_at       TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_quill_notes_board
  ON quill_notes (visibility, owner_profile_id, status, pinned, position);

Household labels live in the existing key-value table: howard_store key quill_settings → { labels: ['groceries','pets', …] }.

8API & sync

A new server/domains/quill.js handler, registered in server/http.js after the existing four. Every route reads the caller profile with helpers.getCallerProfile and checks the permission matrix before touching the database.

Sync changes

  • cache.js: add quill to domainRevisions and bumpRevision, with a per-profile projection cache like projectedHowardCache.
  • Sync token grows to five revision segments: bootId:profile:h.c.b.f.q. Update getSyncTokenForProfile, parseSyncToken (segment check 4 → 5) and the unchanged/partial comparison in the sync route.
  • Client: useHouseholdSync gains a quillSnapshot and the dbInfo default becomes schema 6. App.jsx passes quillSnapshot into a lazy QuillApp and wires an optimisticMutate style handler.
  • Trash purge (7 days) runs at boot and on the existing six-hourly timer in server.js.
Accepted trade-off

Editing a private note bumps the shared quill revision, so the other partner’s device re-fetches an identical projection. That leaks only timing, never content, which is acceptable for a home app. Splitting revisions per visibility is possible later.

Old clients

A cached 4-segment token simply fails to parse and triggers one full sync, which is harmless.

9Concurrency & offline behaviour

Two people editing the same shared note is the realistic hazard. Quill handles it with optimistic concurrency, with no operational transforms or CRDTs needed.

  • Each note has an integer revision. The client sends baseRevision with every full save.
  • If it doesn’t match, the server returns 409 with the current note. The editor shows who changed it and offers Keep mine (re-save on top) or Use theirs (discard the draft).
  • Incoming SSE updates never overwrite an open editor draft. A banner reads “Updated by Partner 2 — reload” instead.
  • Checklist ticks use the item-level PATCH, so two people ticking different items rarely conflict at all.
  • Pin, colour, archive and reorder are field-level PATCHes: last write wins on those fields only.
  • Autosave debounces at about 600 ms, flushes on blur, modal close and pagehide (via keepalive fetch, already supported by apiRequest), and shows “Saving… / Saved / Couldn’t save — retrying”.
  • If the server is unreachable the existing amber “Reconnecting” banner appears; the draft stays in the editor and retries. There is no offline queue by design.

12Testing & verification

Automated (node --test)

  • Privacy: Partner 1’s sync payload never contains Partner 2’s private notes (and vice versa); Caregiver sees only caregiverVisible notes.
  • Permissions: 404 for foreign private notes; Caregiver writes rejected.
  • Concurrency: stale baseRevision returns 409 with the current note.
  • Ordering: midpoint inserts, end inserts and renormalisation when the gap is below 1e-6.
  • Trash: purge removes only notes trashed more than 7 days ago.
  • Migration: v5 → v6 adds quill to profiles exactly once; fresh install keeps quill_notes.
  • Limits: oversize title/body/items/labels are rejected.
  • Markdown-lite: parser unit tests, including that <script> and javascript: links render as inert text.
  • Backup: export/restore round trip in replace and merge modes.

Manual checklist

  • Two browsers as two profiles: edit the same shared note, see the 409 flow.
  • Live SSE update appears on the second device without refresh.
  • Drag with mouse, then with touch (real phone or emulator); page still scrolls normally.
  • Keyboard-only: move a tile, open, edit, close.
  • Warm and Dark themes: all twelve colours readable.
  • 375 px wide viewport: two columns, editor as full-screen sheet.
  • Restart the container: notes, order and pins persist.

14Open questions

Decisions needed from you
  1. Name. Quill is the working title. Alternatives: Pinboard, Jotter, Scribe.
  2. Caregiver access. Should the sitter see read-only “House Notes” and be able to tick checklist items, or should Quill be partners-only?
  3. Backups. Should a full backup exported by Partner 1 include Partner 2’s private notes? (Floodgate’s precedent is that full backups include them by default, with an opt-out.)
  4. Images. Do you want photos on notes later? It would need a storage decision (files on disk vs blobs in SQLite) and a larger upload limit than the current 5 MB JSON cap.
  5. Dependencies. Are you happy to stay dependency-free (custom drag and Markdown-lite), or would you accept one library (@dnd-kit for dragging, TipTap for WYSIWYG) for a richer feel?
